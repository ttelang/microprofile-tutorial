== Overview

The MicroProfile Catalog Service in Chapter 4 builds upon the foundation established in earlier chapters by introducing advanced MicroProfile OpenAPI 4.1 features and multi-persistence architecture patterns. This service provides a RESTful API for product catalog management with enhanced OpenAPI capabilities.

This project demonstrates the key capabilities of MicroProfile OpenAPI 4.1, CDI qualifiers for flexible architecture, and dual persistence implementation switching between JPA/Derby database and in-memory storage.

== What's New in Chapter 4

This chapter focuses on:

* *MicroProfile OpenAPI 4.1 Enhancements* - Java Records, Optional fields, extensible interfaces, and async operations
* *Flexible Persistence Architecture* - Ability to switch between JPA and in-memory implementations via CDI qualifiers
* *Advanced OpenAPI Features* - Comprehensive security documentation, callback support for async operations

For foundational concepts including REST API design, layered architecture, CDI basics, and Derby database setup, refer to Chapters 2 and 3.

== Flexible Persistence Architecture

The application implements a flexible persistence layer with two implementations that can be switched via CDI qualifiers:

1. *JPA/Derby Database Implementation* (Default) - For production use with persistent data storage
2. *In-Memory Implementation* - For development, testing, and scenarios where persistence across restarts is not required

=== CDI Qualifiers for Implementation Switching

The application uses CDI qualifiers to select between different persistence implementations:

[source,java]
----
// JPA Qualifier
@Qualifier
@Retention(RUNTIME)
@Target({METHOD, FIELD, PARAMETER, TYPE})
public @interface JPA {
}

// In-Memory Qualifier  
@Qualifier
@Retention(RUNTIME)
@Target({METHOD, FIELD, PARAMETER, TYPE})
public @interface InMemory {
}
----

=== Service Layer with CDI Injection

The service layer uses CDI qualifiers to inject the appropriate repository implementation:

[source,java]
----
@ApplicationScoped
public class ProductService {
    
    @Inject
    @JPA  // Uses Derby database implementation by default
    private ProductRepositoryInterface repository;
    
    public List<Product> findAllProducts() {
        return repository.findAllProducts();
    }
    // ... other service methods
}
----

To switch to in-memory implementation, use:

[source,java]
----
@Inject
@InMemory  // Switches to in-memory implementation
private ProductRepositoryInterface repository;
----

=== Implementation Comparison

[cols="1,1,1", options="header"]
|===
| Feature | JPA/Derby Implementation | In-Memory Implementation
| Data Persistence | Survives application restarts | Lost on restart
| Performance | Database I/O overhead | Fastest access (memory)
| Configuration | Requires datasource setup | No configuration needed
| Dependencies | Derby JARs, JPA provider | None (Java built-ins)
| Threading | JPA managed transactions | ConcurrentHashMap + AtomicLong
| Development Setup | Database initialization | Immediate startup
| Production Use | Recommended for production | Development/testing only
| Scalability | Database connection limits | Memory limitations
| Data Integrity | ACID transactions | Thread-safe operations
| Error Handling | Database exceptions | Simple validation
|===

=== When to Use Each Implementation

*Use JPA/Derby Implementation When:*
* Data persistence across restarts is required
* Working with large datasets that benefit from database optimization
* ACID transaction guarantees are critical
* Multiple application instances need to share data

*Use In-Memory Implementation When:*
* Rapid prototyping and development
* Unit and integration testing
* Stateless containerized deployments
* Working in environments where database setup is not desired

== Architecture

The application follows a layered architecture pattern:

* *REST Layer* (`ProductResource`) - Handles HTTP requests and responses
* *Service Layer* (`ProductService`) - Contains business logic
* *Repository Layer* (`ProductRepositoryInterface` implementations) - Manages data access
* *Model Layer* (`Product`) - Represents the business entities

== Switching Between Implementations

To switch between JPA and in-memory implementations, modify the `@Inject` annotation in `ProductService`:

[source,java]
----
// Use JPA Implementation (default)
@Inject
@JPA
private ProductRepositoryInterface repository;

// OR use In-Memory Implementation
@Inject
@InMemory
private ProductRepositoryInterface repository;
----

Alternatively, use MicroProfile Config to externalize this decision:

[source,bash]
----
# In microprofile-config.properties
product.repository.impl=jpa  # or "inmemory"
----

== Performance Considerations

The in-memory data store provides excellent performance for read operations, but consider:

* *Memory Usage*: Large data sets may consume significant memory
* *Persistence*: Data is lost when the application restarts
* *Scalability*: In a multi-instance deployment, each instance will have its own data store

For production scenarios, the JPA/Derby implementation is recommended.

== Troubleshooting

=== Common Issues

* *OpenAPI documentation not available*: Ensure `mp.openapi.scan=true` is set in microprofile-config.properties
* *Implementation not switching*: Verify the @Inject qualifier matches a valid repository implementation
* *Database errors with JPA implementation*: Check Derby datasource configuration in server.xml
* *Concurrent modification exceptions*: Ensure proper use of thread-safe collections (in-memory implementation)
